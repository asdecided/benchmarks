\section{Related work}

\paragraph{Context use in coding agents.}
SWE-ContextBench~\citep{swecontextbench2026} is the closest neighbour: it
evaluates whether coding agents reuse prior \emph{experience} across related
GitHub issues and pull requests, and finds that accurately retrieved and
summarised context improves resolution accuracy and reduces runtime and token
cost, whereas unfiltered or wrongly-selected context provides limited or negative
benefit. We share its premise---context selection quality matters, and bad
context can hurt---and its treatment of token cost as a first-class metric. We
differ in three ways. First, our unit of knowledge is a \emph{durable governing
decision} (ADR- or standard-like), not an episodic task solution. Second, our
discriminating signal is \emph{machine-stated supersession}: following the live
decision and dropping the one it supersedes, a case generic retrieval need not
get right. Third, our scoring is deterministic and structural rather than
end-to-end resolution accuracy, trading breadth for reproducibility and a sharp,
single-variable comparison.

\paragraph{Issue resolution benchmarks and the SWE lineage.}
SWE-bench~\citep{swebench} established realistic, execution-verified evaluation of
coding agents on GitHub issues. \benchname{} positions itself explicitly in that
lineage: SWE-bench evaluates issue \emph{resolution}; SWE-ContextBench
\citep{swecontextbench2026} evaluates episodic \emph{context retrieval}; and
\benchname{} evaluates durable governing-\emph{decision} adherence, together
with decision-conditioned resolution as its executable co-primary outcome. We
use the family name to state that position, not to claim any affiliation with or
endorsement by the SWE-bench authors. \benchname{} is complementary to the
resolution benchmarks: its novel construct does not ask whether a patch passes
tests, but whether the agent's proposed change \emph{adheres} to the decision
that governs it.

\paragraph{Version-conditioned code generation.}
GitChameleon~\citep{gitchameleon} evaluates code generation against pinned
library versions with executable unit tests --- the version pin is exactly a
recorded engineering decision an ungrounded model violates from memory. Our
executable co-primary outcome adapts it: each problem's pin becomes a typed
decision artifact among real distractor pins, the prompt never restates the
pinned version, and the upstream harness's tests remain the sole scorer. Under
that protocol our numbers are an arm comparison, not comparable to the
GitChameleon leaderboard, whose prompts state the version explicitly.

\paragraph{Retrieval and memory.}
Retrieval-augmented generation~\citep{rag} is the \texttt{naive\_rag} baseline
here---a fair, strong baseline using asymmetric query/document embeddings, not a
strawman. Memory and experience-reuse benchmarks (e.g.\ MemoryBench
\citep{memorybench}) report retrieval hit-rate metrics analogous to our
governing-decision recall, which we use to explain \emph{why} adherence moves
rather than as an end in itself.
